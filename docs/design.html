SLM-FINTECH · design v0.1 · draft for review

SLM Fintech Platform: design, architecture and implementation plan

A multi-tenant API that lets fintech clients send financial documents and get structured JSON back, using a small language model hosted in our own AWS account. A chatbot API comes later and reuses the same foundation.

Status Draft Date 13 Oct 2026 Scope now Document extraction Reserved Chat API

AWS architecture

Everything that waits for requests is serverless and costs close to nothing when idle. The only machine that costs money by the hour is the GPU worker, and it runs only during business hours.

Request flow

The upload request waits up to 40 seconds. If the document is finished by then, the response is 200 with the JSON result, so one call is enough. Otherwise it is 202 with the job ID, and the client calls GET /v1/extractions/{id}?wait=40 again. Outside business hours the answer is 202 at once. Files up to 5 MB go in one multipart request; larger files use a presigned upload (below).

Extraction pipeline

File type is decided from the file's bytes, never its name. Digital documents send only text to the model, which uses far fewer tokens than page images.

  D -->|PDF| P{"Text layer on every page?"}
  D -->|DOCX| X["LibreOffice headless → PDF

  D -->|"JPG / PNG"| I["Fix rotation, strip EXIF,

  G --> M

  V --> C["Consistency checks
totals · balances · PAN format"]
  C --> K["Masking
Aadhaar always, others per tenant"]
  K --> O["result.json + warnings"]

Fig. 4 One model handles text and images, so there is only one model to deploy, evaluate and fine-tune.

  • Forced JSON output. vLLM's guided decoding constrains the model to the document type's JSON schema, so the output always parses.
  • Untrusted content. The prompt tells the model that the document is data, not instructions. The model has no tools, so text planted in a document cannot trigger any action.
  • Consistency checks add warnings rather than failing the job, for example "subtotal + tax does not equal total". Clients can route those documents to human review.
  • Amounts are returned as decimal strings ("11800.00") so no precision is lost to floating point.
  • Limits: 20 pages per document, 25 MB per file (5 MB for direct upload). Encrypted PDFs are rejected with a clear error.

Choosing between 4B and 8B

Build a labelled test set of about 30–50 real, anonymised documents per type. Run both models and compare accuracy per field. Pick 4B if it is within about 2 percentage points of 8B, because it processes pages faster on the same GPU. Also test any documents that contain Hindi or regional languages.

GPU sizing

Qwen3-VL-8B in FP8 takes about 10 GB of the L4's 24 GB, which leaves room for a 32k-token context and batching. The L4 supports FP8 natively; the older T4 does not, which is why the T4 option needs 4-bit AWQ. One GPU also serves every tenant's LoRA adapter, so adding tenants does not add GPUs.

Region choice and cost

A US region such as us-east-1 is usually about 10–20% cheaper for GPUs than Mumbai. On this design that is roughly $10–25 a month.

Recommendation: stay in Mumbai (ap-south-1). RBI rules require payment data to be stored in India, and its digital-lending and outsourcing guidelines lead banks, NBFCs and lending apps to require India hosting in their contracts. Hosting abroad would save a small amount but could rule out the clients this platform is for. Hyderabad (ap-south-2) can serve as the disaster-recovery region later.

The time of day does not change the price much. Spot prices move with demand, not with a daily cycle, so the business-hours schedule is where the saving comes from.

Tenant isolation and data model

  1. The tenant comes from the API key, never from the request. Keys are random, shown once and stored only as SHA-256 hashes.
  2. IAM enforces isolation. Each request assumes a role tagged with its tenant ID. The role may only touch DynamoDB keys that start with TENANT#<id> and S3 keys under tenants/<id>/. If the code has a bug, AWS still refuses access to another tenant's data.
  3. Original file names are not stored (for example aadhaar_rahul_sharma.jpg). Only the detected type and size are kept.
  4. No document content in logs. Application logs hold IDs, status and timings only. A separate audit log records who did what and when.

A secondary index (GSI1: TENANT#<id>, JOB#<created_at>) lists a tenant's jobs newest first. Extracted data is never stored in DynamoDB; it lives in S3, and the job item holds a pointer.

Training on stored data

  • Only tenants who opt in have files kept beyond processing. Otherwise the uploaded file is deleted as soon as the result is written.
  • Corrections from POST …/corrections are the most valuable training data.
  • Each tenant gets its own LoRA adapter trained only on its data, so one tenant's data cannot leak into another's results. The shared base model is improved only with de-identified or synthetic data.
  • Every dataset and adapter records which jobs it used, so an erasure request can be traced and the affected adapter retrained.
  • A new model or adapter goes live only if it beats the current one on a fixed test set for each document type.

Implementation plan

Durations assume one or two developers and are rough. Each phase ends with something that can be demonstrated.

Phase 0 · Local foundation week 1

  • Repository, uv project, Dockerfile, docker-compose (moto, api, worker, ollama)
  • Settings, app factory, error format, health check
  • Script that creates local table, bucket, queues and a demo tenant
Done when docker compose up gives a running API that answers authenticated requests.

Phase 1 · Tenancy and jobs weeks 1–2

  • API keys, auth and scopes; tenant settings
  • DynamoDB repositories with tenant-prefixed keys; S3 store; SQS queue
  • Upload, submit, get, list, delete endpoints; reserved chat routes
  • Tests proving one tenant cannot read another's jobs
Done when a job goes from upload to queued and back through the API, with the fake model.

Phase 2 · Extraction pipeline weeks 2–3

  • Type detection, PDF, DOCX and image preprocessing
  • Model gateway (OpenAI-compatible) with forced JSON output
  • Five schemas with consistency checks; masking (Aadhaar always)
  • Worker with retries, dead-letter queue, deduplication, usage counters, webhooks
Done when real sample documents of all five types return correct JSON locally through Ollama.

Phase 3 · Accuracy evaluation weeks 3–4

  • Collect 30–50 anonymised documents per type and label the expected JSON
  • Scoring script: accuracy per field and per type
  • Compare Qwen3-VL 4B and 8B; tune prompts and preprocessing
Done when the model choice is made from measured accuracy and the targets per type are agreed.

Phase 4 · AWS deployment weeks 4–5

  • Terraform for ap-south-1: VPC and endpoints, DynamoDB, S3 with lifecycle rules, SQS, KMS, Lambda, API Gateway, WAF
  • GPU worker on ECS with Spot and on-demand fallback; business-hours schedule
  • Per-tenant IAM role; region-restriction policy; CloudTrail, GuardDuty, budget alerts
  • CI/CD: tests, image build, deploy
Done when the same end-to-end test passes against the AWS stack.

Phase 5 · Pilot week 6

  • One pilot tenant; dashboards for queue depth, failures and GPU hours
  • Security review and penetration test of the API; incident runbook
Done when the pilot tenant processes real traffic for two weeks within the agreed accuracy.

Later · Training and chat

  • Training dataset export, LoRA training per tenant, gated releases
  • Chat module: sessions in DynamoDB, retrieval with S3 Vectors, streaming replies
